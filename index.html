1. 背景と全体目標

現行システムでは TensorFlow と旧来アーキテクチャを用い、寿司の種類（クラス）ごとに認識を行い得点付けをしています。このアプローチには以下の課題があります。

  • 特定の寿司ネタ（クラス）に強く依存しており、新しいネタを追加するたびに複雑な再学習が必要になる。
  • 新しい桶（丸型・角型・人数違いなど）への拡張が難しい。
  • 詳細なアノテーションが必要で、運用コストが高くなりがち。

本提案書の主な目的は以下の通りです。

  • AIコアの設計を刷新し、個々の寿司ネタ識別への依存を減らし、レイアウト・個数・間隔・整列・バランスといった観点で評価できるようにする。
  • 新しい桶・新しいネタを追加しても、評価精度が落ちない仕組みを整える。
  • 将来的に以下を実現できる基盤を準備する。
    • パフォーマンス改善（1〜2秒/枚のレスポンス）。
    • KDシステムとの連携（KD連携）。
    • 段階的な継続学習（Continuous Learning）の構築。

2. 新アーキテクチャ選定の理由

本案件のポイントは、以下の2つのバランスをどのように取るかです。

  • 盛り付け評価のための輪郭・レイアウト情報の精度
  • 現場で使える推論速度・運用性

検討の過程で、以下のような選択肢を比較しました。

  • YOLO 系（YOLO11 / YOLO11-seg 等）
    従来の YOLO は矩形（Bounding Box）のみでしたが、最新の YOLO11-seg ではセグメンテーションマスクも出力できるようになり、精度次第では本案件にも適用可能です。 一方で、「桶の中で寿司同士が密集している」「行単位での整列や間隔評価が必要」という要件を満たすためには、マスク精度の検証が重要となります。
  • AWS Rekognition / Rekognition Custom Labels
    POC には便利ですが、以下の制約があります。
    • ロジックのきめ細かなカスタマイズが難しい。
    • モデルをモバイル／エッジ側へ出力する柔軟性が低い。
    • 大規模な運用時のコストが高くなりやすい。

そこで、本提案では次のような方針を取ります。

  • 1ヶ月目：YOLO11-seg による検証（速度重視の選択肢）
    • YOLO11-seg を用いて、桶・寿司ピース・サイド（ガリ等）のマスク精度と速度を検証します。
    • もし「行単位の整列」「隣接との間隔」「桶の縁からの距離」など、評価に必要な幾何情報が十分に取れる場合は、そのまま YOLO ベースでフェーズ1の実装を進めます。
  • YOLO の精度が要件を満たさない場合：Mask R-CNN + PyTorch へ切り替え
    • YOLO では一部のケースでマスク／輪郭精度が不足する場合、インスタンスセグメンテーションに実績のある Mask R-CNN を採用します。
    • Mask R-CNN は、寿司ピースごとの輪郭と形状情報を高精度に取得でき、細かいレイアウト評価との相性が非常に良いです。

このように、最初の1ヶ月で YOLO11-seg の可能性を最大限試したうえで、 必要に応じて Mask R-CNN へ切り替える構成とすることで、速度と精度の両面から最適なアーキテクチャを選択できるようにします。

3. 全体アーキテクチャと桶テンプレート

3.1 Mask R-CNN を用いた論理アーキテクチャ

新アーキテクチャにおける基本フローは以下の通りです。

  • スマートフォンアプリから寿司桶の写真を撮影し、AIサーバへアップロード。
  • AIサーバ側で YOLO11-seg または Mask R-CNN（PyTorch）を用いて以下を実施。
    • 寿司、ガリ、軍艦巻き、巻き物など、各ピースごとにセグメンテーション（輪郭抽出）。
    • 桶（丸型／角型）の輪郭・形状の認識。
  • Rule Engine が桶テンプレートと評価ルール群を適用し、総合スコアを算出。
  • クライアント（モバイル／他システム）に JSON 形式で結果を返却。
YOLO11-seg または Mask R-CNN によって各寿司ピースの輪郭を高精度に取得し、Rule Engine 側で 重心・主軸・距離・平行性などの幾何情報を算出することで、詳細な盛り付け評価を可能にします。

3.2 「桶テンプレート（Box Template）」の定義

桶テンプレート（Box Template） は、桶ごとのマスタ設定です。 評価ロジックをコード側にハードコーディングするのではなく、次のように役割分担します。

  • AIモデル： 「見る」部分を担当し、各寿司ピースの位置・輪郭・形状を認識します。
  • 桶テンプレート + ルールエンジン： 「評価する」部分を担当し、桶ごとの理想レイアウトと比較しながら採点します。

各桶ごとのテンプレートには、主に以下の情報を保持します。

  • ゾーン数／行数／列数などの構造。
  • 各ゾーンに期待される寿司の個数。
  • レイアウトパターン（例：3行×10貫、上下2段構成など）。
  • 各行・ゾーンの桶の中心からの相対位置（上下バランスや整列評価に利用）。
  • 最低限、寿司の種類を細かく識別しなくても、個数とレイアウトが正しければ評価できる構成。

テンプレート適用時のフローは以下の通りです。

  1. AI が寿司ピースと桶の輪郭をセグメント。
  2. 桶の形状（丸／角）と相対サイズ情報から、該当する桶テンプレートを選択。
  3. 各寿司ピースを、正規化した座標を用いてテンプレート上のゾーンにマッピング。
  4. 以下の観点でルールを適用。
    • 各ゾーンの寿司個数は期待値通りか。
    • 各行が平行か、直線上に揃っているか、間隔が適切か。
    • 桶の中心に対して上下・左右のバランスが取れているか。
角型桶に対するテンプレート例：桶をゾーン・行・列に分割し、各ゾーンごとの期待個数を定義。 AI が検出した各寿司ピースをテンプレート上に配置し、理想レイアウトとのズレを Rule Engine で評価します。
同一テンプレートに属する2つの盛り付け例： Image1 は標準パターン、Image2 は同じテンプレート定義のまま貫数・行数を増やしたバリエーションです。 テンプレート側で「行・ゾーン・期待個数」を定義しておくことで、ネタが増えても評価ロジックを共通化できます。

3.3 画像評価フロー

1枚の画像に対する基本的な評価フローは次の通りです。

  1. モバイルアプリから画像を受信。
  2. 画像の正規化（リサイズ・正規化など）。
  3. YOLO11-seg または Mask R-CNN による推論：
    • 寿司、ガリ、軍艦、巻き物等の各ピースをセグメント。
    • 桶の輪郭をセグメント。
  4. 座標を正規化し、対応する桶テンプレートにマッピング。
  5. 10個の評価ルール（新ルールセット。寿司種類依存度を下げたもの）を適用。
  6. 総合点・減点理由・OK/NG 判定を集計。
  7. 結果を JSON 形式でクライアントに返却。

4. フェーズ1 – 新しい桶・寿司に対応するAIコア

4.1 フェーズ1の目標

  • 新しい桶（丸型・角型・人数違いなど）に対応できるようにする。
  • 新しいパターン追加時に、全体の再学習を必要以上に行わず、柔軟に拡張できる構造にする。
  • 個々の寿司ネタの詳細な種類認識に依存せず、以下を満たすような評価ロジックとする。
    • 桶定義どおりの寿司個数が確保されていること。
    • レイアウト（位置・間隔・整列・バランスなど）が基準を満たしていること。
  • TensorFlow ベースの旧モデルを段階的に置き換える形で、YOLO11-seg / Mask R-CNN + PyTorch による新AIモデルを導入する。

4.2 技術アプローチ（YOLO11-seg / Mask R-CNN + テンプレート）

従来のように寿司を細かいクラスごとに識別するのではなく、フェーズ1では以下にフォーカスします。

  • YOLO11-seg または Mask R-CNN により、寿司ピースを「形状オブジェクト」として検出（インスタンスセグメンテーション）。
  • ルール用に重要となる形状グループを大まかに判別。
    • 一般的な握り寿司。
    • ガリ（黄色・ピンク系の色、特徴的な形状）。
    • 軍艦巻き（楕円形 + 海苔の黒い縁）。
    • 細巻きなどの巻き寿司（円形 + 黒い縁 + 中央に白いシャリ）。
  • モデル上のクラス定義（例） 実際の学習・推論では、個々のネタ名（サーモン、マグロ等）ではなく、以下のようなクラスIDに集約します。
    • TRAY：桶／トレー本体の輪郭
    • SUSHI_MAIN：一般的な握り寿司（ネタは問わない）
    • SUSHI_MAKI：巻き寿司（細巻き・太巻きなど）
    • SUSHI_GUNKAN：軍艦巻き
    • SIDE_GINGER：ガリ
    • SIDE_OTHER：その他の付け合わせ（大葉、レモン、山葵 等）

    これにより、「20種類以上のネタをそれぞれクラス分けして学習する」方式から、 「レイアウト評価に必要な観点だけをクラスに切り出す」方式に切り替えることができます。

  • 各桶ごとに「桶テンプレート」を用意し、ゾーン数・行数・列数・個数を定義。
  • 以下の観点に基づいたルールを適用。
    • レイアウト（行・列の並び）。
    • 位置（相対位置・間隔・平行性など）。
    • 個数（各ゾーンの寿司数）。

これにより、ネタのクラスIDに強く依存せずに、現行に近い、あるいはそれ以上の評価を実現することを目指します。

「皮目の向き」に関するルールについて

現行ルール： 「まち・しめさばのみ、皮目が左に向いていること」 このルールは特定のネタを高精度に識別する必要があり、新しい桶・新しいネタへの拡張を阻害する要因となります。

フェーズ1の提案：

  • 本ルールはフェーズ1の範囲から外すことを提案します。まずは桶・ネタ拡張と全体安定を優先します。
  • 「向きの統一」という考え方を残す場合は、フェーズ2/3の高度ルールとして扱います。
    • 「皮目」があるようなテクスチャを持つ寿司のグルーピング。
    • 同一グループ内での相対的な向きの揃い具合を評価。

4.3 フェーズ1の開発範囲

  1. AIサーバアーキテクチャの再設計
    • 新規 Mask R-CNN モデル（PyTorch）の設計・実装。
    • レイアウト／位置／個数を重視した新しいルールエンジンの設計・実装。
  2. 評価APIの設計
    • 例：POST /api/v1/sushi/score （画像アップロード → スコア・OK/NG・減点理由を含む JSON を返却）。
  3. 「桶テンプレート」向けデータ構造の設計
    • 各桶ごとの設定（ゾーン・行・列など）を DB として管理。
  4. 既存10ルールをベースにしつつ、寿司種類への依存度を下げた新ルールセットの構築
    • 主にレイアウト・位置・個数に基づく評価ロジックへの再設計。
  5. 必要最小限のテンプレート管理用画面／ツールの設計・実装
    • 新しい桶テンプレートの登録・編集。
    • 行数／列数／期待個数／ゾーン位置の設定。
  6. 将来の「管理された継続学習」に向けた基盤整備
    • 画像＋評価結果の保存。
    • 難しいケース（Hard Case）のマーキング機能の準備。

4.3.1 本フェーズで扱う寿司クラス（クラス数と役割）

フェーズ1では、ネタごとの細かい種類（マグロ・サーモン等）ではなく、 盛り付け評価に必要な6種類のクラスに集約して学習・推論を行います。

  • TRAY：桶そのもの（丸桶・角桶）。テンプレートとの対応付けに使用。
  • SUSHI_MAIN：一般的な握り寿司（シャリ＋ネタの1貫）。
  • SUSHI_MAKI：巻き寿司（細巻き・太巻きなど、円形断面を持つロール）。
  • SUSHI_GUNKAN：軍艦巻き（海苔で囲まれた楕円形の寿司）。
  • SIDE_GINGER：ガリ（ショウガ）。ガリゾーンの判定・異物チェックに利用。
  • SIDE_OTHER：その他の付け合わせ（ワサビ、飾り、仕切りパーツ等）。

Mask R-CNN は画像からこれら6クラスをインスタンス単位で検出し、 各インスタンスの輪郭・重心・面積・向きなどの幾何情報を出力します。 ルールエンジン側では、この幾何情報と桶テンプレート（Row・ゾーン・期待個数）の情報を組み合わせて採点を行います。

4.3.2 テンプレート方式に対応した採点ルール例（10ルール）

現行の10ルールと同等レベルのチェックを、テンプレート方式＋6クラスで再定義します。 それぞれのルールは 0〜10 点のスコアを持ち、合計 100 点からの減点方式（または加点方式）で総合点を算出します。

ルール 評価観点（テンプレートとクラスの利用イメージ） 主に利用するクラス
Rule 1：総貫数 テンプレートに定義された expected_total_pieces と、 SUSHI_MAIN / SUSHI_MAKI / SUSHI_GUNKAN の検出数を比較。 差が0なら満点、差が1〜2貫なら減点、小さすぎ／多すぎの場合は大きく減点。 SUSHI_MAIN, SUSHI_MAKI, SUSHI_GUNKAN
Rule 2：行ごとの貫数 桶テンプレート上の各 Row に対して「期待貫数」を定義。 各寿司ピースの重心をテンプレート座標にマッピングし、Rowごとに個数をカウント。 行ごとの個数がテンプレートと一致していれば満点、±1貫で減点。 SUSHI_MAIN, SUSHI_MAKI, SUSHI_GUNKAN, TRAY
Rule 3：行の直線性・平行性 Rowごとに寿司の重心を直線フィッティングし、 直線の角度と残差（どれだけ直線からズレているか）を算出。 テンプレートの行角度（row_angle_deg）とのズレが許容範囲内なら満点。 SUSHI_MAIN, SUSHI_MAKI, SUSHI_GUNKAN
Rule 4：行間の間隔 上下の Row の中心線の距離を比較し、 テンプレートに定義された row_gap_px_ratio と比べてバラつきが小さければ満点。 行間が詰まりすぎ／空きすぎの場合は減点。 SUSHI_MAIN, SUSHI_MAKI, SUSHI_GUNKAN, TRAY
Rule 5：桶の縁とのマージン 各寿司ピースの重心から桶の縁（TRAY マスク）までの距離を計測。 edge_margin_ratio（「桶の内側何％以内」など）の範囲に収まっていれば満点。 縁に近すぎる／中央に寄りすぎる行には減点。 SUSHI_MAIN, SUSHI_MAKI, SUSHI_GUNKAN, TRAY
Rule 6：ガリゾーン テンプレート上で「Ginger Zone」を定義し、 そこに SIDE_GINGER が1〜数個だけ存在するかを確認。 ゾーン外にガリがある、またはまったく無い場合は減点。 SIDE_GINGER, TRAY
Rule 7：巻き物／軍艦の配置 一部のテンプレートでは、SUSHI_MAKI / SUSHI_GUNKAN を 特定の Row またはゾーンにまとめて配置するルールを定義。 テンプレートのゾーン内に所定数があるか、他のゾーンに散らばっていないかをチェック。 SUSHI_MAKI, SUSHI_GUNKAN, TRAY
Rule 8：左右・上下バランス TRAY の中心線で上下／左右に分割し、各側の寿司ピース数・面積の合計を比較。 上下／左右のバランスがテンプレート比 ±○％以内なら満点。 SUSHI_MAIN, SUSHI_MAKI, SUSHI_GUNKAN, TRAY
Rule 9：重なり・異常配置 寿司どうしのマスクの重なり具合（IoU）を確認し、 極端な重なりや、SIDE_OTHER / SUSHI_* がテンプレート外に大きくはみ出していないかをチェック。 異常なオーバーラップや飛び出しがある場合に減点。 SUSHI_MAIN, SUSHI_MAKI, SUSHI_GUNKAN, SIDE_OTHER, TRAY
Rule 10：空白・欠け テンプレート上で寿司が入るべきゾーンに大きな空白領域がないかを確認。 連続した空白ゾーンがある場合や、Row中央に穴が空いている場合には減点。 SUSHI_MAIN, SUSHI_MAKI, SUSHI_GUNKAN, TRAY

スコアリングのイメージ：

  • 各ルールを 0〜10 点で評価し、合計 100 点満点とします。
  • 80 点以上：OK（良好）／ 60〜79 点：要注意／ 59 点以下：NG など、 しきい値は要件定義時に御社とすり合わせの上で決定します。
  • テンプレート定義を変更（行数・期待個数・ゾーン）することで、 新しい桶やバリエーションにも同じルールセットをそのまま適用できます。

4.4 使用技術

フェーズ1では、AI部分とアプリケーション部分を明確に分離します。

  • AI部分（新規構築）
    • YOLO11-seg / Mask R-CNN（PyTorch）： 寿司ピース・ガリ・軍艦・巻き物などをインスタンスセグメンテーション。
    • Python：推論サービスおよびルールエンジンロジックの実装。
    • S3 などのオブジェクトストレージ：学習用画像・データセット・モデルの保存。
    • GPU/CPU サーバ：初期学習と推論の実行環境。
  • アプリケーション部分
    • アプリケーションバックエンド： 現行システムで利用中の Ruby on Rails（RoR）等のスタックをベースに想定。
      • モバイルアプリ向け API の提供。
      • AIサービス（Python）の呼び出し。

      • 桶テンプレートの管理。

4.5 フェーズ1終了後に対応可能な桶種

フェーズ1（2,000時間）を前提とした対応範囲のイメージは以下の通りです。

  • 丸型桶グループ
    • 現在運用中の主要な丸型桶（1人前・2人前など、定型レイアウトのもの）。
    • 上記と類似レイアウトの新丸型桶（行数・貫数が多少異なるバリエーション）で、テンプレートで表現可能なもの。
  • 角型桶グループ
    • 生産で主に利用される標準的な角型桶（本提案でターゲットとするパターン）。
    • 行数や列数が異なるが、同系統レイアウトの角型桶（例：行を1つ増やす、列を2つ増やす等）。
  • ネタに関して
    • 対象桶の中で使用されるネタ（握り・軍艦・細巻き等）については、以下のレベルを想定します。
      • サーモン・マグロなど魚種の厳密識別までは行わず、以下を重視。
        • 総貫数が定義どおりであるか。
        • 各ゾーン・各行ごとの個数が定義どおりであるか。
        • 行の整列、上下左右のバランス、間隔が適切であるか。
    • 「皮目があるネタ」や「サイズが大きく異なる軍艦」「多層の巻き物」など、 特殊なルールが必要なネタは、フェーズ2/3での強化対象として整理します。

実際にどの桶・どのレイアウトをフェーズ1の対象とするかは、要件定義フェーズで御社とすり合わせさせていただきます。

4.6 新しい桶・ネタを追加しても評価精度を維持するための条件

新たな桶・ネタを追加した際に、評価の安定性を保つための考え方は以下の通りです。

  • 桶追加時
    • 既存桶と大きく異なる「自由配置」ではなく、行・列ベースで表現可能なレイアウトであること。
    • 行数／列数／ゾーン構成と、各ゾーンの期待貫数をテンプレートで定義できること。
    • 基本的なルール（整列・端との距離・バランス等）が流用可能であること。
  • ネタ追加時
    • 魚種が変わるだけでレイアウトが同じ場合： テンプレート側の設定（例えば「ここには◯貫」など）を修正するだけで済み、モデル再学習は不要なケースもあります。
    • 形状が大きく異なるネタ（極端に高さがある、非常に大きい等）の場合：
      • 既存の形状クラス（握り・軍艦・巻き物等）で表現可能かどうかを検討。
      • 必要に応じて、新しい形状グループとして学習対象に追加（次回学習タイミングで対応）。
  • 運用面
    • 新しい桶を追加する際は、以下の運用を推奨します。
      • テンプレートを追加。
      • 実際の生産写真でテストし、安定性を確認。
    • 短期間に多くの桶・レイアウトが追加される場合は、3〜6ヶ月単位で定期的な再学習計画を立ち、モデルが多様な画像に慣れるよう運用します。

4.7 アーキテクチャと継続学習フロー概要

  • 4.7.1 初期AIモデル構築

    ユーザー → 画像アップロード → AIモデル（YOLO11-seg / Mask R-CNN + ルールエンジン） → 評価結果を返却

5. フェーズ2 – パフォーマンス改善（1〜2秒）

5.1 フェーズ2の目標

フェーズ1で精度・ルール・対象桶が安定して運用できることを確認した上で、フェーズ2では以下を目標とします。

  • 1枚あたりの処理時間を1〜2秒程度まで短縮（環境・画像サイズに依存）。
  • スマートフォンで撮影 → 即時に近い形で評価結果が返るユーザー体験の実現。

5.2 最適化内容の詳細

AIモデルの最適化

  • Mask R-CNN / YOLO11-seg のチューニング
    • Mask R-CNN 側では、ResNet-50-FPN 系のバックボーンを前提としつつ、 入力画像サイズや特徴量の数、Proposal 数などを調整することで軽量化・高速化を図ります。
    • YOLO11-seg 側では、MobileNet-v2/v3 などの軽量バックボーン構成も含めて検証し、 精度と速度のバランスが最も良い構成を選定します。
  • AIコア内での不要処理の削減
    • 不要な後処理の削除・簡略化。
    • 得点計算に影響が少ない幾何計算の簡素化。
  • 識別に十分な範囲で画像解像度を下げ、推論速度を向上。
  • Python Runtime の最適化
    • 入出力処理の改善。
    • 不要なDBアクセスの削減。
    • バッチ処理や接続プールの導入検討。

サーバ・インフラの最適化

  • 以下の条件を満たす場合、GPU導入を検討。
    • モデル部分の推論時間を 80〜120ms 未満にしたい場合。
    • リクエスト数が多く、並列処理が必要な場合。
    • 高解像度の画像が多い場合。
  • メモリ・CPU の最適化
    • モデルをあらかじめメモリ上にロードし、起動オーバーヘッドを削減。
    • ワーカープロセスやバッチングの最適化。
  • 並列リクエスト処理に耐えられる構成
    • Webサーバ／アプリケーションサーバのスケールアウト。
  • 画像処理オーバーヘッドの削減
    • アップロード画像のフォーマット制限（JPEG推奨等）。
    • クライアント側での事前リサイズ。

モバイル側の最適化

  • アップロード画像サイズの規定
    • 例：最長辺 1,024〜1,600px 程度（詳細は要件定義時に協議）。
  • JPEG など適切な圧縮形式の利用。
  • 必要に応じて
    • 通信状態が悪い場合のリトライロジック。
    • アップロードや判定進捗の UI 表示。

計測と改善サイクル

パフォーマンス最適化のため、モニタリング基盤を整備し、以下の指標を取得します。

  • リクエスト単位の指標
    • Upload time：クライアント→AIサーバへのアップロード時間。
    • Decode time：画像の読込・デコード時間。
    • Preprocess time：モデル入力用の前処理時間。
    • Inference time：YOLO11-seg / Mask R-CNN の推論時間。
    • AI Core time：モデル+ルールエンジンを含むAI処理全体時間。
    • Response time：クライアントへの応答完了までの総時間。
  • サーバ全体の指標
    • Average latency：平均レイテンシ。
    • P95 / P99：95%/99% のリクエストがこれより早く処理される時間。
    • Error rate：エラー発生率。
    • Model confidence distribution：モデルの信頼度分布（難しいケースの把握）。

これらの指標をもとに、モデル構成・サーバ構成・画像サイズ等の組み合わせを試験し、コストとスピードのバランスが最も良い構成を選定します。

6. フェーズ3 – KDシステム連携 & 継続学習

6.1 フェーズ3の目標

  • KDシステムから共通のAIサーバを呼び出し、画像評価を行えるようにする（KD連携）。
  • 以下を実現するための基盤を構築する。
    • 生産現場で撮影された画像と評価結果の蓄積。
    • 学習価値の高い画像の選別と、学習パイプラインへの投入。
    • AIプロジェクトをゼロからやり直すことなく、段階的に精度を向上させる仕組み。

6.2 KD連携（KDシステムとの連携）

KD と AIサーバ間の API インターフェースは以下を想定します。

  • KDシステムから、評価対象画像または画像URLを送信。
  • AI側は以下を含む詳細な評価結果を返却。
    • OK / NG 判定。
    • スコア。
    • 各ルールごとの減点理由。
  • 安定運用のための仕組み
    • APIバージョン管理（v1, v2 ...）：モデルやロジックが変更されても KD 側の運用が影響を受けないようにする。
    • ログ・監査：リクエスト数、処理時間、エラー履歴等の記録。

6.3 継続学習（Continuous Learning）

継続学習の推奨フロー：

  1. データ保存
    • 全ての画像と、その時点の AI 評価結果をデータレイク（S3 + DB）に保存。
    • 特に以下の画像を別キューとして管理。
      • モデル信頼度が低い（閾値未満）ケース。
      • 検知結果に異常があると判定されたケース。
  2. Hard Case Queue の運用
    • 難しいケース（Hard Case）を集約したキューを作成。
    • QC/リーダー向けの画面で、AI判定結果の確認と正解ラベリングを行えるようにする。
  3. 定期的な再学習サイクル
    • 3〜6ヶ月ごとに再学習プロジェクトを立ち上げ。
    • 学習データセットは以下の組み合わせで構成。
      • 既存の安定データセット。
      • Hard Case から選別した画像。
      • 検証用の標準テスト画像。
  4. 新モデルの評価・デプロイ
    • 標準テストセットで新旧モデルを比較評価。
    • 既存モデルより良い場合に限り、本番モデルとしてデプロイ。
    • 性能が劣る場合は、既存モデルを維持し、新モデルは候補として保管。

自動化レベルについて：

  • 初期段階では「人手による確認を前提とした継続学習」とし、常に人間のレビューを挟みます。
  • 運用が安定し、データが蓄積してきた段階で、徐々に自動化の比率を高めつつも、いつでもロールバックできる仕組みを維持します。

8. サーバインフラ費用（開発環境・本番環境）

現行システム（TensorFlow ベース）は、高スペック構成で運用されており、サーバ費用として月額40〜50万円程度が発生している状況と理解しております。

新アーキテクチャ（YOLO11-seg / Mask R-CNN + PyTorch）では、最適化次第でリソース効率の改善が見込めますが、安定した推論のためには一定レベルのサーバ性能が必要となります。

8.1 開発環境向けインフラ

  • AI開発用サーバ：
    • GPU付きEC2（または同等サービス）を1台想定。 初期学習および検証時のみ起動し、学習が終わり次第停止することでコストを抑えます。
  • アプリケーション開発／ステージング環境：
    • CPUベースのサーバを1〜2台（アプリケーション＋DB）想定。
  • 開発環境の月額コスト目安：
    • GPU利用時間にもよりますが、数万円／月 程度からコントロール可能と考えています。

8.2 本番環境向けインフラ

  • AI推論サーバ：
    • CPU高性能サーバまたは小規模GPUサーバを1台（トラフィックに応じてスケールアウト）。
  • アプリケーションサーバ：
    • Webアプリケーションサーバを1〜2台。 現行インフラの一部流用も検討可能です。
  • データベース & ストレージ：
